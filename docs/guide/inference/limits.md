# 사용 한도

엔드포인트를 안정적으로 운영하려면 세 층위의 한도를 알아 둬야 합니다. 모델 자체의
컨텍스트 길이, 엔드포인트의 레플리카 상한, 그리고 호출에 쓰는 키에 걸린 요청·토큰 한도.
셋은 서로 다른 곳에서 설정되고 서로 다른 방식으로 요청을 막습니다.

## 컨텍스트 길이 — max_model_len

VLLM 계열 워크로드는 `workload_config.max_model_len` 으로 한 요청이 다룰 수 있는 최대
토큰 수(프롬프트 + 생성분 합계)를 정합니다. 이 값을 넘는 프롬프트를 보내면 `422` 로
거부됩니다.

```json
{ "workload_config": { "max_model_len": 4096 } }
```

이 값은 모델 자체가 학습된 최대 컨텍스트를 넘을 수 없습니다. 긴 문서를 요약하거나 대화
히스토리를 통째로 넣는 용도라면, 엔드포인트를 만들 때 모델이 지원하는 한도 안에서
넉넉하게 잡아 두는 편이 나중에 재배포하는 것보다 편합니다. 값을 올릴수록 파드가 쓰는
메모리(KV 캐시)도 커진다는 점은 감안하세요.

## 레플리카 상한 — min_replica / max_replica

엔드포인트는 `min_replica`~`max_replica` 범위에서 파드 수가 자동으로 조절됩니다.
`max_replica` 가 곧 이 엔드포인트가 동시에 처리할 수 있는 파드 수의 상한입니다 — 그
이상으로 트래픽이 몰리면 새 파드가 더 뜨지 않고, 이미 떠 있는 파드들이 요청을 큐잉하며
처리합니다.

| 필드 | 기본값 | 의미 |
|---|---|---|
| `min_replica` | `0` | 유휴 시 최소 파드 수. `0` 이면 Scale-to-Zero |
| `max_replica` | `1` | 트래픽이 몰렸을 때 늘어날 수 있는 최대 파드 수 |

지속적으로 트래픽이 많은 엔드포인트라면 `max_replica` 를 늘려 병렬 처리량을 확보합니다.
레플리카와 콜드 스타트의 관계는 [콜드 스타트와 Scale-to-Zero](/guide/inference/cold-start)
를 참고하세요.

## 키 단위 한도 — RPS / RPM / 월 토큰

추론 요청에 쓰는 키(또는 인증이 없는 환경이라면 엔드포인트 자체)에는 다음 세 축의
한도를 걸 수 있습니다.

| 한도 | 단위 | 초과 시 |
|---|---|---|
| RPS | 초당 요청 수 | `429` |
| RPM | 분당 요청 수 | `429` |
| 월 토큰 | 월 누적 `total_tokens` | `429` (또는 환경에 따라 다른 차단 방식) |

이 한도는 [Admin AI Inference 앱](/admin/) 에서 키별로 설정하고 조회합니다.

## 동시 요청

레플리카 상한과 별개로, 파드 한 대가 동시에 처리하는 요청 수도 실질적인 처리량을
좌우합니다. vLLM 은 배치 처리로 여러 요청을 함께 다루지만, 요청이 몰리면 응답 시간이
늘어나는 방식으로 나타납니다(요청이 거부되기보다는 대기열에서 지연됩니다). 처리량이
꾸준히 부족하다면 `max_replica` 를 늘리거나, 리소스 사이징(CPU/메모리, GPU 개수)을
키우는 두 방향을 함께 검토하세요.

## 429 를 받았을 때

`429` 는 어느 한도에 걸렸는지에 따라 원인이 다릅니다.

- **RPS/RPM 초과** → 짧은 시간에 요청이 몰린 것입니다. 지수 백오프로 재시도하면 대개
  다음 시도에서 성공합니다. 재시도 코드 예제는 [에러 처리](/guide/inference/errors) 를
  참고하세요.
- **월 토큰 한도 초과** → 그 달 안에는 같은 키로 더 이상 요청이 통과하지 않습니다.
  재시도로 해결되지 않으므로 관리자 앱에서 한도를 확인하고 조정을 요청하세요.

두 경우를 구분하려면 응답 본문의 에러 메시지를 확인하거나, 관리자 앱의 사용량 화면에서
어느 축이 한도에 닿았는지 조회합니다.
